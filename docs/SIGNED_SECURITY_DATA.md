# Signed security-data updates

Data-only protocol. No downloaded JavaScript, native code, executable launch, browser credential forwarding or remote trust-key replacement. Active source: `assets/companion/security-updates.js`; native commit path: `updateSecurityData` in `src/protection/protection.cpp`. It is shipped **unconfigured**, not falsely advertised as an operating feed.

## Trust and payload

`security-update-policy.json` contains an app-shipped public SPKI key, allowed HTTPS source/prefix and enabled flag. No private key belongs in source. Envelope schema1 carries exact UTF8 JSON bytes as base64 plus RSA-PSS/SHA256 signature, salt32. Keys2048–4096bits. Signed payload declares product `MaenBrowser-security-data`, app minimum version, strictly increasing safe-integer sequence, issue/expiry time(max31days), and three ads/adult/violence list URLs, exact byte sizes and SHA256.

Client rejects wrong signature/algorithm/product, expired/future/stale payload, insufficient app version, untrusted HTTPS origin/path, embedded credentials, redirects, oversized data, incorrect hashes and invalid/noncanonical domains. Publisher combines both reviewed ad sources into the signed ads list and carries all license notices. Individual lists are bounded4MiB and the combined canonical JSON transaction5MiB(native request/encrypted-read caps6MiB). Body sizes are bounded; UTF8 decode is strict. Lists are data, never interpreted as scriptlets. Current equal sequence is an authenticated no-op; lower sequence is rejected. Network or signature failure keeps installed lists active, including offline or expired feeds.

Native endpoint already requires the exact trusted companion origin and blocks agent writes. The new operation independently validates domain counts/order/size, settings revision, native protected sequence and parent PIN when Family is enabled **or a parent PIN already exists**. All three lists are stored in a single DPAPI-protected file with atomic replacement and backup. There is no partial3-file update. Missing primary with retained backup or unreadable protected data does not silently reset the security floor. Family classification merges signed data with bundled categories; parent allow/block/allow-only/PIN settings are not relaxed. Family tables remain lazy while Family is off; no per-request disk/network work.

**Boundary:** signature verification runs in the trusted companion. Native code does not independently verify RSA. Compromise of that privileged extension context is outside this transport's signature boundary, just as it is for existing native controls; parent PIN still applies. DPAPI protects OS-user state, not a hostile administrator or an attacker resetting the entire same-user profile. No absolute anti-rollback claim against OS/profile restoration. SHA checkpoints elsewhere are not signature checks.

## Publisher provisioning

1. Generate a publisher-owned RSA-PSS signing key in a secure signing environment/HSM or protected offline system; retain recovery/rotation ownership. Do not commit/upload the private key with the source or chat download package.
2. Set only the base64 DER SPKI public key and enabled flag in `assets/companion/security-update-policy.json`; distribute that root in a publisher-signed application package. Keep default raw.githubusercontent.com feed/origin/prefix or review CSP and protocol changes for a different publisher service.
3. Configure `MAEN_SECURITY_SIGNING_KEY_PEM` as an encrypted GitHub Actions secret owned by the publisher. The workflow prepares a14day signed feed on reviewed filter changes, weekly renewal or manual dispatch. A missing key yields a visible notice and no feed; ordinary pushes are not broken to pretend signing exists.
4. Inspect the artifact and license notices. `tools/verify-security-feed.py` verifies it against the exact app public root and all bytes before optional publication. Private key material is not written to artifacts.
5. Only if the owner explicitly sets repository variable `MAEN_ENABLE_SECURITY_DATA_PUBLISH=true`, the separate publisher job may create/update `security-data`. Its contents-write token is scoped to that job. It publishes immutable sequence directories, notices and `current.json`, rejecting stale sequences. Application `main` is not changed. Source upload alone does not enable publication.
6. Sequence convention: UTC `YYYYMMDDHHMMSS`, always strictly greater than every previously accepted sequence. Do not switch from a larger number to a smaller date format. Source/root updates and key rotation require a signed app update, not trust-on-first-use from the network.

Client checks at most once per daily alarm and on explicit request; no always-running update process. A parent-required notification links only to local settings, not a feed-supplied URL. Silent parent-PIN bypass is intentionally unavailable; there is no persisted cleartext PIN. Android currently receives reviewed filter updates through signed Play/app packages; the desktop companion client is not falsely claimed as an Android extension.

Files: `tools/build-security-feed.py`, `verify-security-feed.py`, `.github/workflows/security-data.yml`. `python -m pip install -r tools/requirements-release.txt` is a build-time test/signing dependency, not a browser runtime component. Existing third-party notices/licenses travel with signed artifacts. Existing manual HTTPS ad-filter update remains separate and does not claim a publisher signature; signed bundle remains authoritative after restart.
