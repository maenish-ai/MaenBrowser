# Audit progress — 2026-11-07

Baseline: `cfd93ba2c9505757a68948b49be0dc257349a0b0` (GitHub main). This is a targeted review and not proof that every line has been reviewed or that vulnerabilities are absent.

## Change
Android WebView request filtering now parses and validates the HTTPS hostname once per request and passes the same host into both existing family and advertising domain checks. Fail-closed family readiness and filter precedence remain unchanged. Runtime performance impact has not been measured on a device.

## Security and compatibility evidence
- Android WebView rejects TLS errors and disables mixed content, local file access and content access. Windows rejects explicit sandbox/TLS bypass startup switches; these source observations are not a complete penetration test.
- Windows CEF codec build remains pinned at Chromium 154.0.8037.98. The official CEF stable comparison on this date reports Chromium 156.0.8078.80. See `research/2026-11-07/engine.json`; version comparisons do not establish actual exploitability or backports. A new codec-enabled CEF must be built and tested as a whole before promoting the lock.
- `research/2026-11-07/browser-kev.json` is an official CISA-derived historical browser-related set, not a list of confirmed MaenBrowser vulnerabilities.
- Existing code explicitly does not implement CEF legacy programmatic extension loading. Chrome Runtime extension support is partial; neither universal extension support nor Android Chrome extension support is established.
- H.264/AAC and several formats have prior Windows CI playback evidence; not every codec, device, WebRTC workflow or service has been tested. Authenticated ChatGPT, Manus, WhatsApp, Telegram, screen sharing and calls require real account/device tests.
- The installed Windows build, security update signing and real memory/CPU measurements on 4/8/16 GB hardware remain release prerequisites. See `RELEASE_BLOCKERS.md`. Do not claim full production readiness.
